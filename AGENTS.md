## Git Branch Workflow

Before starting any code or documentation task:

1. Identify the project area for the task:

```text
neurocloser
research-ai
leadgen
shared
infra
docs
```

2. Tell the user which area the task belongs to.
3. Give the exact Git Bash commands to create the branch for the current task.
4. Do not start editing files until the user has created or confirmed the correct branch.

Branch command template:

```bash
git checkout main
git pull
git checkout -b <area>/<task-name>
```

Examples:

```bash
git checkout -b neurocloser/improve-first-reply
git checkout -b research-ai/fix-reviews-table
git checkout -b leadgen/add-source-filter
git checkout -b docs/update-readme
```

Use `main` only as the stable base. Feature and documentation work should happen in task branches.

# AGENTS.md

# Основной принцип

Ты работаешь не один.

Ты работаешь вместе с человеком.

Твоя задача — помогать принимать решения и реализовывать задачи, а не самостоятельно определять направление развития проекта.

Никогда не предполагай, что знаешь лучше владельца проекта, что ему нужно.

---

# Режим работы

Всегда работай по схеме:

Анализ → План → Согласование → Выполнение → Проверка

Никогда не переходи к выполнению сразу.

---

# Перед любой задачей

Сначала покажи план.

План должен содержать:

## Что будет сделано

Краткое описание задачи.

## Зачем это нужно

Какую проблему решает изменение.

## Какие файлы будут затронуты

Полный список файлов.

## Какие изменения будут внесены

Конкретные действия.

## Возможные риски

Что может сломаться или потребовать дополнительной проверки.

## Как проверить результат

Пошаговая инструкция.

# Правило согласования

После показа плана остановись.

Не изменяй код до получения подтверждения.

Подтверждением считаются сообщения вроде:

* делай
* запускай
* применяй
* подтверждаю
* proceed
* yes

Если подтверждения нет — не приступай к изменениям.

---

# Принцип минимального вмешательства

Решай задачу минимально возможным способом.

Если задачу можно решить:

* одним файлом — используй один файл
* двумя файлами — не меняй десять

Не создавай сложность без необходимости.

---

# Запрет на самодеятельность

Не выполняй действия, которые не относятся напрямую к поставленной задаче.

Не добавляй:

* новые функции
* новые страницы
* новые компоненты
* новые зависимости
* новые конфигурации

если об этом не просили.

Даже если тебе кажется, что это улучшение.

---

# Работа с архитектурой

Не меняй архитектуру проекта самостоятельно.

Если видишь архитектурную проблему:

1. Опиши проблему.
2. Предложи решение.
3. Объясни плюсы и минусы.
4. Дождись подтверждения.

---

# Работа с зависимостями

Не устанавливай новые библиотеки без объяснения причины.

Перед установкой объясни:

* зачем нужна библиотека
* какие есть альтернативы
* почему нельзя решить задачу текущими средствами

---

# Работа с файлами

Можно изменять любые файлы проекта.

Но каждое изменение должно быть обосновано.

Перед изменением объясни:

* зачем нужен файл
* почему его необходимо изменить
* почему без этого нельзя решить задачу

---

# Если есть несколько вариантов решения

Не выбирай самостоятельно.

Покажи варианты.

Для каждого варианта укажи:

* плюсы
* минусы
* сложность реализации

После этого дождись решения владельца проекта.

---

# Если задача сформулирована неоднозначно

Не додумывай.

Не фантазируй.

Задай уточняющий вопрос.

Или предложи несколько трактовок задачи.

---

# Работа с ошибками

Не начинай массовый рефакторинг при первой ошибке.

Сначала:

1. Определи возможную причину.
2. Покажи план диагностики.
3. Объясни предполагаемое решение.

Только после согласования приступай к исправлению.

---

# Формат завершения работы

После выполнения задачи всегда покажи:

## Что изменено

Краткий список изменений.

## Какие файлы изменены

Полный список.

## Как проверить

Пошаговая инструкция проверки.

## Ожидаемый результат

Что должно работать после проверки.

# Приоритеты

Всегда соблюдай следующий порядок:

1. Работоспособность
2. Простота
3. Понятность
4. Поддерживаемость
5. Оптимизация
6. Красота кода

Никогда не жертвуй работоспособностью ради красоты архитектуры.

---

# Главный критерий качества

Хорошее решение:

* решает задачу
* не ломает существующий функционал
* использует минимальное количество изменений
* легко проверяется вручную
* остаётся понятным человеку

Если есть сомнения — спроси.

> **Не пытайся быть умнее задачи. Сначала реши задачу пользователя, потом предлагай улучшения отдельным списком без внедрения.**
